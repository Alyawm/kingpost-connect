# KingPost Connect — Structural Collaboration Desktop: Plan A→Z

> **KingPost Connect** is a desktop application for structural engineers to view, review and coordinate structural models and drawings. It occupies the space Trimble Connect occupies, but is built for structural work specifically.

Decisions made so far:

| Decision | Choice |
|---|---|
| Product name | **KingPost Connect** |
| Platform order | Desktop first (Windows primary; macOS/Linux builds come free with the stack) |
| Stack | **Tauri 2 (Rust) + React + TypeScript + three.js / That Open Engine** |
| Niche features | Analysis model viewing · Structural review workflow · Drawing↔model linking · (Quantities & schedules — last, optional) |
| Trimble interop | None. Standalone, local‑first; our own cloud/sync is a later phase |
| Source control | GitHub repository (free account), updated at **milestones only**, curated history for future developers |
| AI policy | **No AI/GPT features in the product and no AI references anywhere in the repository** (code, comments, docs, commit messages, metadata) |

---

## 0. Ground rules

**Legal and ethical**
- Trimble Connect's code, 3D engine, TrimBim format and converters are proprietary. **We do not decompile, copy or re‑implement from their binaries.** Study is limited to *what* the product does, how it is organised, and the shape of its *public* API (shipped with XML docs and a CHM).
- Everything we build comes from open standards — **IFC (ISO 16739), BCF, SAF, PDF** — and open‑source libraries with licences compatible with a commercial product (MIT/BSD/Apache/MPL preferred; AGPL avoided or isolated).
- Keep a `THIRD_PARTY_NOTICES.md` from day one.

**AI policy (client requirement)**
- The product contains no AI assistant, no language‑model integration, no "smart" features marketed as AI. (Trimble ships an `agentic-platform-sdk` bridge; we deliberately do not.)
- The repository contains no references to AI tools: no co‑author trailers, no "generated by" lines, no AI mentions in README, CHANGELOG, comments, issue templates or package metadata.
- Commits are authored under the project's git identity only (see §11).

## 1. Vision and scope

**One sentence:** the place where a structural team drops their IFC/analysis models and drawings, reviews and signs off element by element, compares revisions, and keeps drawings and model in step — without a BIM manager in the loop.

**Primary users**
1. Structural design engineer — checks models from the modeller, reviews against analysis, tracks design status.
2. Structural checker / reviewer — raises and closes issues, needs revision diffs and sign‑off trails.
3. Project engineer — needs drawings tied to the model and a clear picture of what changed between issues.

**Out of scope for v1:** authoring geometry, structural analysis/solving, mobile, real‑time multi‑user editing, Revit/Tekla live plugins, AI features of any kind.

## 2. What we learned from Trimble Connect and what we take from it

Static inspection only (file metadata, PE resources, managed metadata, shipped API docs, UI locale strings). No code was decompiled.

| Observed in Trimble Connect | What it tells us | Our equivalent |
|---|---|---|
| .NET Fx 4.8 + WPF shell, **WebView2‑hosted web module** for the "Column Browser" data grid | Even they moved grid/data UI to web tech. Validates Tauri (which also uses WebView2 on Windows). | All UI in React; single stack. |
| Public Desktop API: `Project`, `Model`, `ModelPlacement`, `ModelObject`, typed `Attribute`s (Length/Area/Volume/Mass…), `Filter`s (attribute, type, selection, visual state), `View`, `Viewport.PointPicker`, `Settings` | A clean domain model worth mirroring *conceptually*: objects carry typed properties; filters are first‑class; saved views are objects. | Our core domain model (§4) uses the same nouns, backed by IFC. |
| Column Browser: presets, grouping, sums, rule‑based groups, "select in 3D", CSV export | A quantity‑takeoff grid. Useful, but not the structural differentiator. | Phase 8 "Schedules" (optional, client decision). Selection/colourise stay in the viewer. |
| Separate feature assemblies: `ToDo`, `PointCloud`, `ClashCheck`, `MixedReality`, `Data.Sync` | Modular feature boundaries. | Monorepo packages per feature (§7). |
| `TrimBim` + `TrimBimDiff` — own binary model format and diff tool | Converting IFC into a fast internal format is how they get performance and diffing. | We convert IFC → our own **fragment cache** (binary geometry + SQLite properties), and diff on IFC `GlobalId` + property hashes. |
| SQLite everywhere | Local‑first storage. | SQLite via Rust (`rusqlite`). |
| `SketchUpAPI`, `PotreeConverter` (licensed third‑party engines) | Importers are bought, not built. | Start IFC‑only; add importers behind feature flags later. |
| `agentic-platform-sdk` web bridge | They are adding AI features. | **Not replicated** (client requirement). |

## 6. Risks and how we handle them

| Risk | Mitigation |
|---|---|
| Large IFC performance in WASM/WebGL vs native DirectX | Fragments cache + streaming + LOD; Phase 1 spike on the biggest real model available; WebGPU path when WebView2 enables it |
| IFC quality from different authoring tools | Per‑tool mapping presets; "data quality" report |
| DWG licensing | PDF first; DXF open format; ODA later if customers demand |
| ETABS/SAP formats undocumented in parts | Parse the documented text subset; rely on exported tables for results; keep parsers isolated and fuzz‑tested |
| Scope creep toward a full BIM platform | Every phase has a "done when" tied to a structural engineer's task |
| Free GitHub Actions minutes (private repo: 2 000 min/month, Windows runner counts ×2) | Build on push of milestone tags only; run tests locally; cache Rust/pnpm |
| Small team burnout | Each phase ships something usable; alpha after Phase 1, beta after Phase 2 |

## 11. GitHub repository: purpose, workflow and setup

### Purpose (client requirement)
The repository is the **record of how the program was developed** so future developers can understand it and extend it. That is served by three things, in order of importance:
1. **Readable history** — commits grouped per feature with messages that say *why*, not a single giant dump per milestone.
2. **Decision records** — `docs/adr/NNN-title.md`: context, decision, alternatives, consequences. One per significant technical choice.
3. **Milestone devlogs** — `docs/devlog/YYYY-MM-milestone.md`: what was built, what was measured, what was hard, what is next. Written at each push.

### Workflow: local work, milestone pushes
- Day‑to‑day work happens in the local repository with small commits.
- Before a milestone push the history is **curated**: commits squashed/reordered into a coherent sequence per feature (e.g. `feat(ifc): property extraction to SQLite`, `feat(viewer): section planes`), each buildable on its own.
- Push happens **only at milestones** (end of each phase, tags in §9). Each push includes: updated `CHANGELOG.md`, the devlog page, any new ADRs, and a **GitHub Release** carrying the installer and large sample files.
- Branches: `main` only (always equals the last milestone). No pull requests needed with one team; if a second developer joins, short‑lived feature branches merged into `main` before the milestone push.
- Commit messages: Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `perf:`, `test:`, `chore:`), scope in parentheses, body explains the reasoning. **No co‑author or tool trailers.**

### Free‑account constraints and how we live with them
| Constraint | Consequence |
|---|---|
| Private repos are free with unlimited collaborators | Use a **private** repo; make it public later if the client wishes |
| Git LFS free tier: 1 GB storage, 1 GB bandwidth/month | Do **not** commit large IFC/PDF samples; attach them to GitHub Releases (2 GB per file, no bandwidth cap of that kind) |
| Actions: 2 000 min/month private (Windows runner = 2× minutes) | CI runs only on tag pushes; local testing otherwise |
| Branch protection rules are limited on private free repos | Not needed for this workflow |
| Repository recommended < 1 GB, hard warnings at 5 GB | Curated history + no binaries keeps us far below |

### Setting up the repository (client steps, ~10 minutes)
1. Sign in at github.com with the free account (or create one at github.com/signup).
2. Top‑right **+ → New repository**:
   - Owner: the client account (or a free **Organization** named after the company — recommended so the repo is not tied to one person).
   - Repository name: `kingpost-connect`
   - Description: "Structural collaboration desktop: IFC review, revision comparison, analysis overlay, drawing linking."
   - Visibility: **Private**
   - Leave "Add a README", `.gitignore` and licence **unchecked** (the local scaffold provides them).
   - Create repository.
3. Decide the **git identity** commits will carry — a name and an email. The email may be GitHub's private no‑reply address: Settings → Emails → "Keep my email addresses private" shows `ID+username@users.noreply.github.com`.
4. Provide access for pushing from this machine — pick one:
   - **Option A (recommended): GitHub CLI.** Install from cli.github.com, then in your own terminal run `gh auth login` (choose GitHub.com → HTTPS → Login with a web browser) and complete the browser prompt yourself. After that, pushes from this machine work without sharing any secret with anyone.
   - **Option B: you push.** Everything is prepared locally; you run `git push` yourself at each milestone.
   - Do **not** paste personal access tokens or passwords into chat.
5. (Optional) Settings → General → Features: enable **Issues** and **Discussions** if the client wants to track work on GitHub; disable **Wiki** (docs live in the repo).

### What to send back after setup
- The repository URL, e.g. `https://github.com/<owner>/kingpost-connect`
- The git identity to use: display name and email (no‑reply address is fine)
- Which access option (A or B) was chosen
- The licence the client wants on the code (proprietary "All rights reserved", or an open licence) — this goes into `LICENSE` in the first push

With those four items the first milestone push (`v0.0.1-foundation`) can be prepared.
